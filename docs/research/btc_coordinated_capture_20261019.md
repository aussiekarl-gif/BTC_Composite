# BTC market-flow capture coordination — research only, 19 October 2026

**No live trading changes, no portfolio writes, no new ntfy sender, no paid provider.**

## Identified issue

The two free public market-data collectors were independently scheduled at UTC 01:17/07:17/13:17/19:17 (Kraken) and 01:19/07:19/13:19/19:19 (Coinbase). GitHub Actions cron execution may be delayed independently; actual HTTP capture receipt times can exceed the five-minute pairing limit. The first real snapshots, generated by different merge-triggered jobs, were 7m27s apart and could not be reliably paired. Relaxing the gate would falsely improve sample counts.

## Proposed coordinated implementation

- Replace the two independent cron schedules with **one GitHub Actions runner and one six-hour-cadence schedule**, at UTC 01:17/07:17/13:17/19:17.
- On the same runner, record a Kraken public XBT/USD spot-depth snapshot, then immediately request the latest **bounded Coinbase BTC-USD executed-trade sample**. Actual receipt timestamps, not cron planned time, determine whether a paired observation qualifies. Keep the strict original **five-minute** gate.
- KEEP THE ORIGINAL TWO distinct source CSVs, immutable rows and SHA256 chains exactly as written. No merges, rewrites or fabricated backfill of any old samples.
- Preserve both original source workflows as **manual fallbacks and PR validators** with the same Actions concurrency lock, but remove their regular cron and push-triggered captures to eliminate job collisions and avoid doubling scheduled costs.
- If one provider fails, attempt the other independently. Commit only valid new rows to the original source CSVs, attach both source tapes to GitHub run artifacts, and fail the run with a visible warning **after** preserving the successful observation. Never silently use synthetic substitutes.
- Revalidate immutable tapes before and after each capture. If an existing source chain is corrupt, do not fetch, fabricate or overwrite.
- Run the original frozen forward-scorecard routine as a read-only optional artifact. A scorecard failure must not block the immutable original-source preservation.
- Existing **Cycle Trading daily ntfy** unchanged; no additional user alerts or scheduled ChatGPT messages.

The source collectors are still *sparse*: 100 Coinbase recent trades may cover seconds, not the entire six-hour interval, and Kraken resting depth is not executed buying/selling. Pairing within five minutes is an improved data-quality constraint, not evidence of profitability or independent consensus voting.

## Verification and acceptance

- New offline `tests/test_btc_coordinated_capture.py` checks capture timing, independent provider failures, no double counting, hash chain validation before IO, idempotence, and absence of trading/alerts.
- Existing collector and forward-scorecard tests run in PR and on the first main push. GitHub PR also performs real **read-only probes**, with no saved records.
- On merge, the first coordinated GitHub run captures both live feeds if eligible and safe. The next *scheduled* run checks actual pairing status. If one source is unavailable, keep the valid other's record but do not infer a pair.
- A push conflict with concurrent public market-tape jobs is surfaced rather than force-pushed. Both original data files must retain previous rows exactly.

Research performance remains unproven. No upgrade to the main models, ASX:IBIT buy/sell instructions, BTC alert schedule or SMSF investment decisions is justified by successful API connectivity.
